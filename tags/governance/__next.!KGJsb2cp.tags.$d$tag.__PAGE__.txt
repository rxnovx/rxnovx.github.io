# 핵심 한 줄: LLM 경쟁이 “더 똑똑한 모델”에서 “더 안전하게 연결되는 시스템”으로 이동 중임, MCP는 그 연결 계층을 표준화하려는 시도임.

## 이 글에서 말하는 “모델 중심 → 시스템 중심 전환” 정의

모델 중심이란 파라미터/학습/추론(성능, 비용, 지연, 컨텍스트 길이)에서 대부분의 가치가 결정된다는 관점이고, 시스템 중심이란 모델은 부품이고 실제 성패는 연결(데이터·도구), 제어(권한·정책), 관측(로그·트레이스), 회복(재시도·격리) 같은 런타임 구조에서 갈린다는 관점임.

MCP가 뜨는 배경은 “에이전트가 일을 한다”라는 유행어가 아니라, 에이전트가 일을 하려면 ‘외부 세계’와 연결돼야 하고, 연결은 곧 시스템 문제가 되기 때문임.

---

# MCP가 건드리는 핵심: N×M 통합 지옥을 “프로토콜”로 바꾸려는 시도

## N×M 문제가 왜 구조적으로 터지는지

엔터프라이즈에서 LLM을 실제 업무에 넣는 순간, 모델 하나만 붙이는 게 아니라 다음이 동시에 늘어남.

* 모델 종류 N: 사내/외부, 비용/성능, 지역 규제, 팀별 선호
* 툴/데이터 소스 M: CRM, 티켓, 문서, 결제, 내부 API, RPA, 사내 DB, 서드파티 SaaS

전통 방식(모델별 커스텀 커넥터)은 결국 N models × M tools만큼 어댑터가 필요해지고, 보안·감사·권한 모델이 커넥터마다 달라져서 운영이 무너짐.

MCP는 이걸 호스트-클라이언트-서버 구조로 표준화해서, 모델/앱은 공통 방식으로 “툴 정의를 읽고 호출”하고, 각 툴은 MCP 서버로 캡슐화하자는 접근임.

---

# 시스템 구조 관점에서 본 MCP: 모델이 아니라 “런타임 연결 계층”임

## 텍스트 다이어그램: MCP가 들어간 에이전트 런타임

아래는 “모델이 답변한다”가 아니라 “시스템이 일을 끝낸다”를 기준으로 그린 구조임.

```
[User/UI]
   |
   v
[Agent Runtime]
  - policy(권한/데이터 경계)
  - planner(작업 분해/우선순위)
  - memory(단기/장기, 요약/원문)
  - executor(재시도/타임아웃/격리)
   |
   v
[LLM] <----> [MCP Client] <----(stdio/http/sse)----> [MCP Server: Tool A]
   |                                                 [MCP Server: Tool B]
   |                                                 [MCP Server: Data C]
   v
[Observability]
  - trace(span: tool call)
  - audit(log: who/what/why)
  - eval(정확도/안전/회복률)
```

여기서 “모델 개선”은 LLM 박스만 바꾸는 일이고, “시스템 개선”은 policy/exec/obs를 바꾸는 일임.

MCP가 중요한 지점은 모델 ↔ 도구/데이터 연결을 표준화함으로써, 성능 논쟁을 “모델”에서 “런타임 통제/운영”으로 이동시키는 촉매 역할을 한다는 점임.

---

# 실제 사례 1: AutoGPT류 에이전트가 실패하는 방식은 “모델 부족”보다 “시스템 부재”에 가까웠음

AutoGPT 계열(초기 오픈소스 에이전트들)은 대체로 다음 문제로 터졌음.

* 목표 드리프트: 계획이 길어질수록 목표가 바뀌거나 자기합리화로 진행
* 툴 호출 불확실성: API 입력 형식/제약을 모델이 “추측”해서 실패
* 상태 관리 부재: 중간 산출물, 실패 원인, 재시도 정책이 체계가 아니라 프롬프트에 섞임

이건 “모델이 더 똑똑하면 해결”이 아니라,

* 툴 스키마를 결정적으로 제공하고,
* 실패 시 재시도/롤백/격리 가 있고,
* 실행 내역이 관측 가능 해야 해결되는 부류임.

MCP는 “툴 정의를 공통 규격으로 노출”하는 방향이라서, 최소한 ‘추측 기반 통합’을 줄이려는 설계임.

---

# 실제 사례 2: Devin류(코딩 에이전트)가 보여준 건 “모델 능력”보다 “툴링+운영”의 합성물임

Devin 같은 코딩 에이전트가 인상적으로 보이는 지점은 자연어 답변이 아니라 아래 조합임.

* 레포 클론/빌드/테스트/런을 자동화하는 도구 체인
* 실패 로그를 읽고 수정하는 반복 루프
* 작업 단위를 쪼개고 우선순위를 조정하는 플래너
* 결과물을 PR/이슈 코멘트로 남기는 워크플로우 연결

즉 “모델이 코드를 잘 짠다”라기보다 시스템이 코드 작업을 끝내게 만드는 실행 환경이 핵심임.

---

# 실제 사례 3: 엔터프라이즈 적용은 ‘모델 선택’이 아니라 ‘경계 설계’부터 시작됨

현업 적용에서 반복해서 부딪히는 건 “어떤 모델이 더 좋냐”보다 다음임.

* 어떤 데이터에 접근 가능한지(권한/PII)
* 어떤 툴 호출이 허용되는지(결제/삭제/권한변경)
* 실패했을 때 누가 책임지는지(감사/재현)
* 결과가 왜 그렇게 나왔는지 설명 가능한지(로그/트레이스)

여기서 MCP 같은 표준화 레이어가 의미 있는 이유는, 툴/데이터의 연결이 ‘확장 가능한 형태’로 관리돼야 거버넌스/감사가 가능해지기 때문임.

---

# 개발자 관점: MCP 도입 시 설계 포인트(진짜로 중요한 것들)

## 1) 모델은 교체 가능해야 함

모델을 바꾸는 순간 제품이 망가지는 구조면 이미 모델 중심 구조에 묶인 상태임, MCP는 모델/앱이 툴을 같은 방식으로 보도록 만들지만, “모델 교체 가능”은 별도 설계(프롬프트/툴 스키마/출력 계약)로 확보해야 함.

## 2) 툴 스키마는 ‘문서’가 아니라 ‘계약’이어야 함

도구 호출 정의가 느슨하면 에이전트가 다시 추측을 시작함, 스키마는 입력 검증, 오류 코드, 부작용(쓰기/삭제)까지 포함한 계약이어야 하고, 이를 기반으로 재시도/격리 정책을 짤 수 있어야 함.

## 3) 관측(Observability)은 옵션이 아니라 기능임

에이전트는 실패를 많이 함, 그러면 실패를 재현하고 고쳐야 하는데, 로그가 없으면 운영 불가임, tool call trace, 입력/출력 샘플링, 정책 위반 로그, 사용자 승인 이벤트가 기본 구성임.

## 4) 인간 개입(HITL)은 ‘안전장치’가 아니라 ‘제품 UX’임

결제, 삭제, 권한 변경 같은 고위험 툴은 인간 승인 플로우가 제품 UX로 설계돼야 함, 단순히 “확인해줘” 메시지로 해결하려 하면 결국 운영 사고로 감.

---

# 리스크: MCP가 있다고 시스템 문제가 사라지는 건 아님

## 1) 표준화는 ‘연결’을 쉽게 만들지만 ‘통제’를 자동으로 주지 않음

MCP가 툴 호출을 쉽게 만들어도, 그 툴이 무엇을 할 수 있는지, 누가 호출할 수 있는지, 어떤 조건에서 허용되는지(policy)는 별도 설계임.

## 2) 권한 상승(Privilege Escalation)과 데이터 누출은 더 쉬워질 수 있음

연결이 쉬워지면 공격면도 커짐, MCP 서버가 내부망 자원에 붙는 순간, 인증/인가/감사/비밀키 관리가 구멍이면 단일 지점 침해로 확대됨.

## 3) 에이전트는 ‘정확성’보다 ‘행동’이 위험함

검색 답변 오류는 피해가 제한적일 수 있는데, 삭제/결제/권한변경 같은 행동 오류는 피해가 즉시 발생함, 따라서 모델 평가보다 실행 정책(승인, 제한, 시뮬레이션)이 더 중요해짐.

## 4) 벤더 종속은 프로토콜이 아니라 운영 툴체인에서 생김

프로토콜이 표준이어도, 관측/평가/정책 엔진이 특정 벤더 툴에 묶이면 종속은 그대로 발생함, 시스템 구성 요소를 교체 가능한 형태로 분리해야 함.

---

# 마지막 본질 정리

MCP가 의미 있는 이유는 “새 프로토콜”이라서가 아니라, LLM 활용이 모델 성능 싸움에서 끝나지 않고, 실제로는 연결·권한·관측·회복을 설계하는 시스템 공학 문제로 이동하고 있음을 드러내는 신호라서임, 모델은 교체 가능해지고, 승부는 런타임 설계와 운영 능력에서 갈리는 쪽으로 수렴 중임.

# AI 안전 논의는 왜 항상 늦는가

해외 IT 매체들은 최근 몇 년간 공통된 문제를 지적함. AI 기술은 빠르게 진화하는데, 안전과 규제 논의는 항상 한 박자씩 늦음.

이 글은 WIRED의 AI 안전 관련 분석 기사 흐름을 바탕으로 내용을 재구성한 것임.
원문 URL: [https://www.wired.com/tag/ai-safety/](https://www.wired.com/tag/ai-safety/)

## 기술 발전 속도의 구조적 문제

### 모델 성능은 지수적으로 증가

대규모 언어 모델과 멀티모달 모델의 성능은 단순 개선이 아니라 **질적 도약**에 가까움.
텍스트 생성에서 시작해 코드 작성, 추론, 이미지·음성 생성까지 빠르게 확장됨.

여기서 중요한 점은, 성능 향상이 대부분 **연산량·데이터·모델 크기 증가**에 의해 이루어진다는 사실임.
알고리즘 혁신보다 자원 투입이 더 큰 변수로 작동함.

이 구조는 안전 문제를 더 복잡하게 만듦.
왜냐하면 성능을 멈추지 않는 한 위험도 함께 커지기 때문임.

### 안전 연구는 항상 후행

안전성 평가는 대부분 **이미 배포된 모델**을 기준으로 이루어짐.
즉, 문제가 발생한 뒤에야 대응이 시작됨.

이는 제약이 아니라 구조적 한계에 가까움.
모델 내부 동작은 불투명하고, 실제 사용 환경은 예측 불가능하기 때문임.

추가 정보로, 이 문제를 완화하려는 시도가 바로 RLHF나 헌법형 AI 같은 접근임.
다만 이 역시 사후적 조정에 가깝다는 한계가 있음.

## 규제 논의가 현실을 따라가지 못하는 이유

### 기술 주도권과 국가 경쟁

AI는 단순한 소프트웨어 문제가 아님.
국가 경쟁력, 군사·정보 우위, 산업 패권과 직결됨.

이 때문에 각국 정부는 위험을 인지하면서도 **속도 조절을 꺼림**.
규제가 곧 경쟁력 저하로 이어질 수 있다는 판단 때문임.

이 지점에서 안전 논의는 항상 후순위로 밀림.
명시적으로 반대하지는 않지만, 실행 단계로는 잘 이어지지 않음.

### 규제 대상이 명확하지 않음

기존 산업 규제는 명확한 대상이 있었음.
공장, 제품, 사업자처럼 물리적 실체가 존재했음.

하지만 AI는 다름.
모델, 데이터, 파인튜닝, 배포 방식이 모두 분산돼 있음.

그래서 규제 초점이 자주 흔들림.
모델을 규제할지, 사용을 규제할지, 결과물을 규제할지 합의가 잘 안 됨.

## 실제로 문제가 되는 영역들

### 딥페이크와 정보 신뢰 붕괴

가장 빠르게 현실화된 문제는 딥페이크임.
텍스트·이미지·음성 모두에서 진짜와 가짜 구분이 어려워짐.

이로 인해 정보의 진위 판단 비용이 급격히 상승함.
개인이 아니라 사회 전체의 문제로 확장되는 지점임.

### 자동화된 판단의 책임 문제

AI가 추천·분류·판단에 개입하는 영역이 늘어남.
금융, 채용, 의료, 행정까지 확장 중임.

문제는 결과에 대한 책임 주체가 불분명하다는 점임.
모델 개발자, 서비스 제공자, 사용자 중 누가 책임지는지 명확하지 않음.

### 인간 의존성 증가

일부 연구에서는 사용자가 AI 응답을 과도하게 신뢰하거나 정서적으로 의존하는 경향을 지적함.
아직 인과관계가 명확하다고 보긴 어려움.
다만 무시하기엔 사례가 빠르게 늘고 있음.

## 구조적으로 가능한 선택지

### 1. 사전 배포 기준 강화

완전한 예방은 불가능함.
다만 대규모 배포 전 최소한의 위험 평가 기준을 강제할 수는 있음.

### 2. 투명성 요구

모델 구조 공개가 아니라,
훈련 범위, 사용 제한, 실패 사례에 대한 투명성 확보가 현실적인 대안임.

### 3. 기술 외적 대응 병행

모든 문제를 기술로 해결하려는 접근은 한계가 있음.
미디어 리터러시, 조직 내 검증 절차 같은 비기술적 대응도 필요함.

## 열린 결론

AI 안전 논의가 늦는 이유는 의지가 없어서가 아님.
기술 구조 자체가 안전을 뒤늦게 생각하도록 만들기 때문임.

결국 선택지는 명확함.
속도를 줄이거나, 위험을 감수하거나.
대부분의 사회는 지금까지 후자를 선택해왔음.
