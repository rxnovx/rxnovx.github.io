# 핵심 한 줄: LLM 경쟁이 “더 똑똑한 모델”에서 “더 안전하게 연결되는 시스템”으로 이동 중임, MCP는 그 연결 계층을 표준화하려는 시도임.

## 이 글에서 말하는 “모델 중심 → 시스템 중심 전환” 정의

모델 중심이란 파라미터/학습/추론(성능, 비용, 지연, 컨텍스트 길이)에서 대부분의 가치가 결정된다는 관점이고, 시스템 중심이란 모델은 부품이고 실제 성패는 연결(데이터·도구), 제어(권한·정책), 관측(로그·트레이스), 회복(재시도·격리) 같은 런타임 구조에서 갈린다는 관점임.

MCP가 뜨는 배경은 “에이전트가 일을 한다”라는 유행어가 아니라, 에이전트가 일을 하려면 ‘외부 세계’와 연결돼야 하고, 연결은 곧 시스템 문제가 되기 때문임.

---

# MCP가 건드리는 핵심: N×M 통합 지옥을 “프로토콜”로 바꾸려는 시도

## N×M 문제가 왜 구조적으로 터지는지

엔터프라이즈에서 LLM을 실제 업무에 넣는 순간, 모델 하나만 붙이는 게 아니라 다음이 동시에 늘어남.

* 모델 종류 N: 사내/외부, 비용/성능, 지역 규제, 팀별 선호
* 툴/데이터 소스 M: CRM, 티켓, 문서, 결제, 내부 API, RPA, 사내 DB, 서드파티 SaaS

전통 방식(모델별 커스텀 커넥터)은 결국 N models × M tools만큼 어댑터가 필요해지고, 보안·감사·권한 모델이 커넥터마다 달라져서 운영이 무너짐.

MCP는 이걸 호스트-클라이언트-서버 구조로 표준화해서, 모델/앱은 공통 방식으로 “툴 정의를 읽고 호출”하고, 각 툴은 MCP 서버로 캡슐화하자는 접근임.

---

# 시스템 구조 관점에서 본 MCP: 모델이 아니라 “런타임 연결 계층”임

## 텍스트 다이어그램: MCP가 들어간 에이전트 런타임

아래는 “모델이 답변한다”가 아니라 “시스템이 일을 끝낸다”를 기준으로 그린 구조임.

```
[User/UI]
   |
   v
[Agent Runtime]
  - policy(권한/데이터 경계)
  - planner(작업 분해/우선순위)
  - memory(단기/장기, 요약/원문)
  - executor(재시도/타임아웃/격리)
   |
   v
[LLM] <----> [MCP Client] <----(stdio/http/sse)----> [MCP Server: Tool A]
   |                                                 [MCP Server: Tool B]
   |                                                 [MCP Server: Data C]
   v
[Observability]
  - trace(span: tool call)
  - audit(log: who/what/why)
  - eval(정확도/안전/회복률)
```

여기서 “모델 개선”은 LLM 박스만 바꾸는 일이고, “시스템 개선”은 policy/exec/obs를 바꾸는 일임.

MCP가 중요한 지점은 모델 ↔ 도구/데이터 연결을 표준화함으로써, 성능 논쟁을 “모델”에서 “런타임 통제/운영”으로 이동시키는 촉매 역할을 한다는 점임.

---

# 실제 사례 1: AutoGPT류 에이전트가 실패하는 방식은 “모델 부족”보다 “시스템 부재”에 가까웠음

AutoGPT 계열(초기 오픈소스 에이전트들)은 대체로 다음 문제로 터졌음.

* 목표 드리프트: 계획이 길어질수록 목표가 바뀌거나 자기합리화로 진행
* 툴 호출 불확실성: API 입력 형식/제약을 모델이 “추측”해서 실패
* 상태 관리 부재: 중간 산출물, 실패 원인, 재시도 정책이 체계가 아니라 프롬프트에 섞임

이건 “모델이 더 똑똑하면 해결”이 아니라,

* 툴 스키마를 결정적으로 제공하고,
* 실패 시 재시도/롤백/격리 가 있고,
* 실행 내역이 관측 가능 해야 해결되는 부류임.

MCP는 “툴 정의를 공통 규격으로 노출”하는 방향이라서, 최소한 ‘추측 기반 통합’을 줄이려는 설계임.

---

# 실제 사례 2: Devin류(코딩 에이전트)가 보여준 건 “모델 능력”보다 “툴링+운영”의 합성물임

Devin 같은 코딩 에이전트가 인상적으로 보이는 지점은 자연어 답변이 아니라 아래 조합임.

* 레포 클론/빌드/테스트/런을 자동화하는 도구 체인
* 실패 로그를 읽고 수정하는 반복 루프
* 작업 단위를 쪼개고 우선순위를 조정하는 플래너
* 결과물을 PR/이슈 코멘트로 남기는 워크플로우 연결

즉 “모델이 코드를 잘 짠다”라기보다 시스템이 코드 작업을 끝내게 만드는 실행 환경이 핵심임.

---

# 실제 사례 3: 엔터프라이즈 적용은 ‘모델 선택’이 아니라 ‘경계 설계’부터 시작됨

현업 적용에서 반복해서 부딪히는 건 “어떤 모델이 더 좋냐”보다 다음임.

* 어떤 데이터에 접근 가능한지(권한/PII)
* 어떤 툴 호출이 허용되는지(결제/삭제/권한변경)
* 실패했을 때 누가 책임지는지(감사/재현)
* 결과가 왜 그렇게 나왔는지 설명 가능한지(로그/트레이스)

여기서 MCP 같은 표준화 레이어가 의미 있는 이유는, 툴/데이터의 연결이 ‘확장 가능한 형태’로 관리돼야 거버넌스/감사가 가능해지기 때문임.

---

# 개발자 관점: MCP 도입 시 설계 포인트(진짜로 중요한 것들)

## 1) 모델은 교체 가능해야 함

모델을 바꾸는 순간 제품이 망가지는 구조면 이미 모델 중심 구조에 묶인 상태임, MCP는 모델/앱이 툴을 같은 방식으로 보도록 만들지만, “모델 교체 가능”은 별도 설계(프롬프트/툴 스키마/출력 계약)로 확보해야 함.

## 2) 툴 스키마는 ‘문서’가 아니라 ‘계약’이어야 함

도구 호출 정의가 느슨하면 에이전트가 다시 추측을 시작함, 스키마는 입력 검증, 오류 코드, 부작용(쓰기/삭제)까지 포함한 계약이어야 하고, 이를 기반으로 재시도/격리 정책을 짤 수 있어야 함.

## 3) 관측(Observability)은 옵션이 아니라 기능임

에이전트는 실패를 많이 함, 그러면 실패를 재현하고 고쳐야 하는데, 로그가 없으면 운영 불가임, tool call trace, 입력/출력 샘플링, 정책 위반 로그, 사용자 승인 이벤트가 기본 구성임.

## 4) 인간 개입(HITL)은 ‘안전장치’가 아니라 ‘제품 UX’임

결제, 삭제, 권한 변경 같은 고위험 툴은 인간 승인 플로우가 제품 UX로 설계돼야 함, 단순히 “확인해줘” 메시지로 해결하려 하면 결국 운영 사고로 감.

---

# 리스크: MCP가 있다고 시스템 문제가 사라지는 건 아님

## 1) 표준화는 ‘연결’을 쉽게 만들지만 ‘통제’를 자동으로 주지 않음

MCP가 툴 호출을 쉽게 만들어도, 그 툴이 무엇을 할 수 있는지, 누가 호출할 수 있는지, 어떤 조건에서 허용되는지(policy)는 별도 설계임.

## 2) 권한 상승(Privilege Escalation)과 데이터 누출은 더 쉬워질 수 있음

연결이 쉬워지면 공격면도 커짐, MCP 서버가 내부망 자원에 붙는 순간, 인증/인가/감사/비밀키 관리가 구멍이면 단일 지점 침해로 확대됨.

## 3) 에이전트는 ‘정확성’보다 ‘행동’이 위험함

검색 답변 오류는 피해가 제한적일 수 있는데, 삭제/결제/권한변경 같은 행동 오류는 피해가 즉시 발생함, 따라서 모델 평가보다 실행 정책(승인, 제한, 시뮬레이션)이 더 중요해짐.

## 4) 벤더 종속은 프로토콜이 아니라 운영 툴체인에서 생김

프로토콜이 표준이어도, 관측/평가/정책 엔진이 특정 벤더 툴에 묶이면 종속은 그대로 발생함, 시스템 구성 요소를 교체 가능한 형태로 분리해야 함.

---

# 마지막 본질 정리

MCP가 의미 있는 이유는 “새 프로토콜”이라서가 아니라, LLM 활용이 모델 성능 싸움에서 끝나지 않고, 실제로는 연결·권한·관측·회복을 설계하는 시스템 공학 문제로 이동하고 있음을 드러내는 신호라서임, 모델은 교체 가능해지고, 승부는 런타임 설계와 운영 능력에서 갈리는 쪽으로 수렴 중임.

## 들어가기

리눅스 시스템을 사용하려면 반드시 계정이 필요합니다.
모든 로그인, 모든 작업은 결국 **유저(user)** 단위로 기록되고 제어됩니다.

이때 유저를 직접 하나하나 관리하기보다는,
**그룹을 먼저 만들고 그 그룹에 유저를 소속시키는 방식**이 훨씬 효율적입니다.
권한 관리 측면에서도 그렇고,
실제 운영 환경에서도 이 방식이 기본이 됩니다.

개인적으로는 **유저 관리보다 그룹 관리가 더 중요하고, 더 단순하다**고 느끼는 편입니다.
이 글에서는 그 흐름에 맞춰 그룹 → 유저 순서로 정리합니다.

---

## GROUP

리눅스의 그룹 정보는 `/etc/group` 파일에 저장되어 있습니다.

```bash
cat /etc/group
```

이 파일은 한 줄이 하나의 그룹을 의미하며,
각 줄은 `:` 기준으로 **4개의 컬럼**으로 구성됩니다.

* 그룹 이름
* 그룹 비밀번호 (실제 사용하지 않음)
* GID (Group ID)
* 그룹 구성원 목록

형식은 아래와 같습니다.

```text
group_name:x:GID:user1,user2,user3
```

---

### groupadd : 그룹 생성

새로운 그룹을 생성할 때 사용하는 명령어입니다.

```bash
# sales라는 그룹을 생성
groupadd sales

# fin 이라는 그룹을 생성하고 GID를 2000으로 설정
groupadd -g 2000 fin
```

일반적으로 GID는 자동으로 할당되지만,
조직 정책이나 기존 시스템과의 연계를 위해
직접 지정해야 하는 경우도 종종 있습니다.

---

### groupmod : 그룹 설정 변경

이미 존재하는 그룹의 설정을 변경할 때 사용합니다.

```bash
# sales 그룹의 GID를 3000으로 수정
groupmod -g 3000 sales

# fin 그룹의 이름을 oper로 변경
groupmod -n oper fin
```

운영 중인 시스템에서는
**이미 사용 중인 GID를 변경하는 작업은 매우 신중해야 합니다.**
파일 소유권과 직접적으로 연결되기 때문입니다.

---

### groupdel : 그룹 삭제

그룹을 삭제할 때 사용합니다.

```bash
# oper 그룹을 삭제
groupdel oper
```

해당 그룹을 primary 그룹으로 사용하는 유저가 있다면 삭제되지 않습니다.
이 경우 먼저 유저의 그룹을 변경해야 합니다.

---

## USER

유저 관련 정보는 여러 파일에 나뉘어 관리됩니다.

* `/etc/passwd` : 계정 기본 정보
* `/etc/shadow` : 암호 및 만료 정책
* `/etc/shells` : 로그인 가능한 쉘 목록

`/etc/passwd`의 한 줄은 다음과 같은 구조를 가집니다.

```text
계정명:암호:UID:GID:유저메모:홈디렉토리:로그인쉘
```

실제 암호는 `/etc/shadow` 파일에 해시 형태로 저장됩니다.

---

### useradd : 유저 생성

새로운 계정을 생성하는 명령어입니다.

주요 옵션은 다음과 같습니다.

* `-u` : UID 지정
* `-c` : 유저 메모(Comment)
* `-r` : 시스템 계정 생성 (UID 1~999)
* `-s` : 로그인 쉘 지정
* `-g` : primary 그룹 지정
* `-G` : secondary 그룹 지정
* `-m` : 홈 디렉토리 생성
* `-d` : 홈 디렉토리 경로 지정

```bash
# tom 이라는 계정을 생성
useradd tom

# user1을 생성하고 UID를 3001, 메모를 "New User"로 설정
useradd -u 3001 -c "New User" user1

# 시스템 계정 derek 생성
useradd -r -s /sbin/nologin -g sys -G sup1 derek

useradd -u 4989 -s /bin/csh -c "010-1111-2222" susan
useradd -r -s /sbin/nologin -g sales -G sshd,kvm,dbus -m -d /oracle ora
```

리눅스에는 **primary 그룹과 secondary 그룹** 개념이 있습니다.

* `-g` : primary 그룹 (기본 소유 그룹)
* `-G` : secondary 그룹 (추가 소속 그룹)

파일 권한과 접근 제어를 이해하려면
이 구분은 반드시 알고 있어야 합니다.

---

### usermod : 유저 설정 변경

이미 존재하는 유저의 설정을 변경할 때 사용합니다.

`useradd`에서 사용하던 옵션 대부분을 그대로 사용할 수 있습니다.

```bash
# susan의 UID를 3030으로 변경하고
# primary 그룹을 sales로, 로그인 쉘을 bash로 변경
usermod -u 3030 -g sales -s /bin/bash susan
```

secondary 그룹을 추가할 때는 `-aG` 옵션을 사용합니다.

```bash
# susan을 기존 그룹은 유지한 채 docker 그룹에 추가
usermod -aG docker susan
```

`-a` 옵션 없이 `-G`만 사용하면
기존 secondary 그룹이 모두 사라지므로 주의해야 합니다.

---

### userdel : 유저 삭제

유저를 삭제할 때 사용하는 명령어입니다.

```bash
# tom은 홈디렉토리까지 삭제
userdel -r tom

# susan은 계정만 삭제, 홈디렉토리는 유지
userdel susan
```

운영 환경에서는
데이터 보존 여부를 반드시 확인한 후 삭제하는 것이 안전합니다.

---

### 특정 유저가 만든 파일 정리

계정은 삭제했지만,
파일 시스템에는 해당 UID를 가진 파일이 남아있는 경우가 많습니다.

```bash
# UID 1701이 소유한 파일 및 디렉토리 삭제
find / -uid 1701 -exec rm -rf {} +
```

소유자가 없는 파일(`-nouser`)을 처리하는 예시는 아래와 같습니다.

```bash
# 소유자가 없는 파일을 /tmp/backup 으로 이동
mkdir /tmp/backup
find / -nouser 2> /dev/null -exec mv {} /tmp/backup \;
```

이 작업은 반드시 신중하게 진행해야 합니다.

## Shadow 파일과 비밀번호 정책

`/etc/shadow` 파일은
유저의 비밀번호와 만료 정책을 관리하는 핵심 파일입니다.

이 파일을 직접 수정하기보다는
`chage` 명령어를 사용하는 것이 일반적입니다.

```bash
# 현재 비밀번호/계정 만료 정책 확인
chage -l user

# 다음 로그인 시 비밀번호 변경 강제
chage -d 0 user

# 비밀번호 최소 사용 기간 7일
chage -m 7 user

# 비밀번호 최대 사용 기간 90일
chage -M 90 user

# 만료 7일 전 경고
chage -W 7 user

# 만료 후 14일 지나면 계정 비활성화
chage -I 14 user

# 계정 만료일 설정
chage -E 2026-12-31 user
```

shadow 파일의 각 필드는 다음 의미를 가집니다.

```text
username:password:lastchg:min:max:warn:inactive:expire:reserved
```

## 계정 생성 시 영향을 주는 설정 파일

### /etc/login.defs

계정 관련 명령어의 **기본 보안 정책**을 정의합니다.

* login
* useradd
* passwd

이 파일은 PAM보다 하위 레벨에서
기본값의 기준이 됩니다.

```bash
PASS_MAX_DAYS 60
PASS_MIN_DAYS 10
UID_MIN       10000
GID_MIN       20000
```

---

### /etc/default/useradd

`useradd` 명령어를 실행할 때
옵션을 주지 않으면 적용되는 기본값입니다.

```bash
INACTIVE=30
```

---

### /etc/skel

새 계정을 생성할 때,
`/etc/skel` 디렉토리 안의 파일과 디렉토리가
사용자의 홈 디렉토리로 그대로 복사됩니다.

```bash
mkdir -p /etc/skel/Data
touch /etc/skel/manual.txt

useradd lunch
passwd lunch
chage -l lunch
```

초기 환경을 표준화할 때 매우 유용한 구조입니다.
