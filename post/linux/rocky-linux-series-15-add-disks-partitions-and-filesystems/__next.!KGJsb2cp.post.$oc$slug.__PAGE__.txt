<h2 id="들어가기" tabindex="-1" data-src-line="4">들어가기 <a class="header-anchor" href="#들어가기" aria-hidden="true">#</a></h2>
<p>리눅스 시스템을 운영하다 보면, 언젠가는 반드시 디스크를 다뤄야 하는 순간이 옵니다.<br>
처음에는 용량이 충분해 보이던 시스템도 로그가 쌓이고, 데이터가 늘어나고, 서비스가 추가되면서 여유 공간이 줄어듭니다.</p>
<p>이번 글에서는 <strong>디스크를 추가하는 순간부터</strong>, 파티션을 나누고, 파일시스템을 만들고, 마운트하고, 스왑과 LVM까지 이어지는 흐름을 한 번에 정리해보려 합니다.</p>
<p>명령어 하나하나를 외우는 글이라기보다는,<br>
<strong>디스크가 리눅스 안에서 어떤 단계로 관리되는지</strong>를 이해하는 데 초점을 맞췄습니다.</p>
<hr>
<h2 id="vm에-디스크-추가하기" tabindex="-1" data-src-line="16">VM에 디스크 추가하기 <a class="header-anchor" href="#vm에-디스크-추가하기" aria-hidden="true">#</a></h2>
<p>실습 환경은 가상머신입니다.<br>
이번 실습에서는 <strong>VMware에서 가상 디스크를 총 4개 추가</strong>한 상태를 기준으로 진행합니다.</p>
<p>운영체제 설치 시 기본 디스크 1개에 더해,<br>
추가 실습을 위해 <strong>동일한 방식으로 1GB 디스크를 3개 더 추가</strong>했습니다.</p>
<p>결과적으로 리눅스 입장에서는 다음과 같은 디스크 구성이 됩니다.</p>
<ul>
<li><code>/dev/sda</code> : 기본 디스크 (OS 설치)</li>
<li><code>/dev/sdb</code> : 실습용 디스크</li>
<li><code>/dev/sdc</code> : LVM 확장 실습용 디스크</li>
<li><code>/dev/sdd</code> : 캐시 및 태깅 실습용 디스크</li>
</ul>
<p>VMware 기준 디스크 추가 절차는 다음과 같습니다.</p>
<ul>
<li>Virtual Machine Settings</li>
<li>Add… → Hard Disk</li>
<li>SCSI → Create a new virtual disk</li>
<li>용량 1GB</li>
<li>이름은 기본값 유지</li>
</ul>
<p>이 단계까지는 운영체제와는 아직 무관합니다.<br>
단순히 <strong>가상 하드웨어를 여러 개 더 꽂은 상태</strong>입니다.</p>
<p>이제 리눅스가 이 디스크들을 어떻게 인식했는지 확인합니다.</p>
<hr>
<h2 id="리눅스에서-디스크-이름이-정해지는-방식" tabindex="-1" data-src-line="46">리눅스에서 디스크 이름이 정해지는 방식 <a class="header-anchor" href="#리눅스에서-디스크-이름이-정해지는-방식" aria-hidden="true">#</a></h2>
<p>리눅스에서 디스크는 장치 파일로 표현됩니다.<br>
인터페이스 종류에 따라 이름 규칙이 다릅니다.</p>
<ul>
<li>SCSI / SAS / SATA / USB → <code>/dev/sdX</code></li>
<li>IDE (구형) → <code>/dev/hdX</code></li>
<li>가상 디스크(KVM, VirtIO) → <code>/dev/vdX</code></li>
</ul>
<p>요즘 시스템에서는 대부분 <code>/dev/sdX</code> 형태를 사용합니다.</p>
<p>여기서 중요한 점은,<br>
<code>X</code>에 해당하는 a, b, c… 순서는 <strong>물리적인 슬롯 순서가 아니라</strong><br>
<strong>커널이 디스크를 인식한 순서</strong>라는 점입니다.</p>
<p>따라서 재부팅이나 하드웨어 구성 변경에 따라 이름이 달라질 수 있습니다.<br>
이것이 UUID를 사용하는 이유이기도 합니다.</p>
<hr>
<h2 id="블록-디바이스-확인하기" tabindex="-1" data-src-line="66">블록 디바이스 확인하기 <a class="header-anchor" href="#블록-디바이스-확인하기" aria-hidden="true">#</a></h2>
<p>디스크를 추가한 뒤 가장 먼저 확인해야 할 명령은 <code>lsblk</code>입니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">lsblk</span>
</code></pre></div></code></pre>
<h3 id="이-단계에서-확인하는-것" tabindex="-1" data-src-line="74">이 단계에서 확인하는 것 <a class="header-anchor" href="#이-단계에서-확인하는-것" aria-hidden="true">#</a></h3>
<p><code>lsblk</code>는 현재 시스템에 연결된 <strong>블록 디바이스의 계층 구조</strong>를 보여줍니다.<br>
처음 보는 독자라면, 여기서 최소한 아래 3가지만 확인하면 됩니다.</p>
<ul>
<li><strong>새 디스크가 잡혔는지</strong> (<code>/dev/sdb</code>, <code>/dev/sdc</code>, <code>/dev/sdd</code>가 보이는지)</li>
<li><strong>파티션이 있는지</strong> (디스크 아래에 <code>sdb1</code>, <code>sdb2</code> 같은 항목이 생겼는지)</li>
<li><strong>마운트가 되었는지</strong> (MOUNTPOINTS 컬럼에 경로가 보이는지)</li>
</ul>
<h3 id="disk--part--lvm-의-의미" tabindex="-1" data-src-line="83">disk / part / lvm 의 의미 <a class="header-anchor" href="#disk--part--lvm-의-의미" aria-hidden="true">#</a></h3>
<p><code>lsblk</code> 출력에서 TYPE 컬럼은 대상의 성격을 말해줍니다.</p>
<ul>
<li><code>disk</code> : 실제 디스크 장치</li>
<li><code>part</code> : 디스크를 나눈 파티션</li>
<li><code>lvm</code> : LVM이 만든 논리 볼륨(실제로 마운트되는 대상)</li>
</ul>
<p>디스크 작업에서는 이 구분이 계속 반복됩니다.</p>
<h3 id="파일시스템과-uuid까지-같이-보고-싶다면" tabindex="-1" data-src-line="93">파일시스템과 UUID까지 같이 보고 싶다면 <a class="header-anchor" href="#파일시스템과-uuid까지-같이-보고-싶다면" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">lsblk -f</span>
</code></pre></div></code></pre>
<p><code>-f</code> 옵션을 붙이면 파일시스템 타입과 UUID를 함께 볼 수 있습니다.<br>
<code>/etc/fstab</code>에 등록할 때 UUID가 필요하므로, 보통 이 옵션까지 같이 씁니다.</p>
<hr>
<h2 id="파티션-테이블과-파티셔닝-도구" tabindex="-1" data-src-line="104">파티션 테이블과 파티셔닝 도구 <a class="header-anchor" href="#파티션-테이블과-파티셔닝-도구" aria-hidden="true">#</a></h2>
<p>디스크를 바로 사용할 수는 없습니다.<br>
먼저 <strong>파티션 테이블</strong>을 만들고, 그 위에 파티션을 생성해야 합니다.</p>
<h3 id="파티션-테이블이-필요한-이유" tabindex="-1" data-src-line="109">파티션 테이블이 필요한 이유 <a class="header-anchor" href="#파티션-테이블이-필요한-이유" aria-hidden="true">#</a></h3>
<p>디스크는 그냥 큰 공간 하나입니다.<br>
파티션 테이블은 이 공간을 <strong>어떻게 나눠 쓸지에 대한 지도</strong>에 가깝습니다.</p>
<ul>
<li>어디부터 어디까지가 1번 파티션인지</li>
<li>어떤 파티션이 부팅에 쓰이는지</li>
<li>논리 파티션을 확장 영역 안에 어떻게 담는지</li>
</ul>
<p>이 정보가 없으면 커널은 디스크를 “나눠진 형태”로 해석할 수 없습니다.</p>
<h3 id="어떤-도구를-쓰면-되는지" tabindex="-1" data-src-line="120">어떤 도구를 쓰면 되는지 <a class="header-anchor" href="#어떤-도구를-쓰면-되는지" aria-hidden="true">#</a></h3>
<p>여기서 자주 사용하는 도구는 세 가지입니다.</p>
<h4 id="fdisk" tabindex="-1" data-src-line="124">fdisk <a class="header-anchor" href="#fdisk" aria-hidden="true">#</a></h4>
<ul>
<li>가장 오래된 파티셔닝 도구</li>
<li>기본적으로 MBR(msdos) 파티션 테이블 사용</li>
<li>2TB 초과 디스크에는 한계</li>
<li>인터페이스가 단순하고 직관적</li>
</ul>
<p>소형 디스크 실습에는 여전히 유용합니다.</p>
<h4 id="gdisk" tabindex="-1" data-src-line="133">gdisk <a class="header-anchor" href="#gdisk" aria-hidden="true">#</a></h4>
<ul>
<li>GPT 파티션 테이블 전용</li>
<li>2TB 이상의 대용량 디스크 지원</li>
<li>fdisk와 유사한 조작 방식</li>
</ul>
<p>현대 서버 환경에서는 사실상 표준입니다.</p>
<h4 id="parted" tabindex="-1" data-src-line="141">parted <a class="header-anchor" href="#parted" aria-hidden="true">#</a></h4>
<ul>
<li>MBR / GPT 모두 지원</li>
<li>비대화형(non-interactive) 사용 가능</li>
<li>자동화 스크립트에 적합</li>
</ul>
<p>다만, 명령이 즉시 반영되기 때문에 실수 시 복구가 어렵습니다.</p>
<h3 id="한-줄-정리" tabindex="-1" data-src-line="149">한 줄 정리 <a class="header-anchor" href="#한-줄-정리" aria-hidden="true">#</a></h3>
<ul>
<li><strong>단순 실습 / 소형 디스크</strong> → <code>fdisk</code></li>
<li><strong>대용량 디스크 / 서버 환경</strong> → <code>gdisk</code></li>
<li><strong>자동화/스크립트</strong> → <code>parted</code></li>
</ul>
<hr>
<h2 id="bios와-uefi-그리고-파티션-테이블" tabindex="-1" data-src-line="157">BIOS와 UEFI, 그리고 파티션 테이블 <a class="header-anchor" href="#bios와-uefi-그리고-파티션-테이블" aria-hidden="true">#</a></h2>
<p>시스템 펌웨어 방식에 따라 기본 파티션 테이블도 달라집니다.</p>
<ul>
<li>BIOS → MBR(msdos)</li>
<li>UEFI → GPT</li>
</ul>
<p>GPT는 파티션 정보를 디스크 전체에 분산 저장하며,<br>
MBR보다 구조적으로 안정적입니다.</p>
<hr>
<h2 id="fdisk로-파티션-생성-흐름" tabindex="-1" data-src-line="169">fdisk로 파티션 생성 흐름 <a class="header-anchor" href="#fdisk로-파티션-생성-흐름" aria-hidden="true">#</a></h2>
<p>이제 실제로 디스크 하나를 선택해 파티션을 생성해봅니다.<br>
이번 실습에서는 <strong>아직 사용되지 않은 <code>/dev/sdb</code> 디스크</strong>를 대상으로 진행합니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>fdisk <span class="hljs-regexp">/dev/</span>sdb
</code></pre></div></code></pre>
<h3 id="실습에서-만들-파티션-구조" tabindex="-1" data-src-line="178">실습에서 만들 파티션 구조 <a class="header-anchor" href="#실습에서-만들-파티션-구조" aria-hidden="true">#</a></h3>
<p>이번 글에서는 개념을 단순하게 보기 위해 <code>/dev/sdb</code>를 아래처럼 사용합니다.</p>
<ul>
<li><code>/dev/sdb1</code> : XFS 파일시스템으로 포맷 후 <code>/red</code>에 마운트</li>
<li>(선택) <code>/dev/sdb2</code> : swap이나 다른 실습용으로 남겨두기</li>
</ul>
<p>실습에서 파티션을 여러 개로 나누는 이유는 “필요해서”라기보다,<br>
파티션 번호와 구조가 어떻게 생기는지 체감하기 위해서입니다.</p>
<h3 id="자주-쓰는-키" tabindex="-1" data-src-line="188">자주 쓰는 키 <a class="header-anchor" href="#자주-쓰는-키" aria-hidden="true">#</a></h3>
<ul>
<li><code>p</code> : 현재 파티션 테이블 출력</li>
<li><code>n</code> : 새 파티션 생성</li>
<li><code>d</code> : 파티션 삭제</li>
<li><code>w</code> : 변경사항 저장 후 종료</li>
</ul>
<h3 id="mbr에서-꼭-알아야-하는-제한" tabindex="-1" data-src-line="195">MBR에서 꼭 알아야 하는 제한 <a class="header-anchor" href="#mbr에서-꼭-알아야-하는-제한" aria-hidden="true">#</a></h3>
<p>MBR 방식에서는</p>
<ul>
<li>primary 최대 4개</li>
<li>logical 파티션은 5번부터 시작</li>
</ul>
<p>이라는 제약이 있습니다.</p>
<p>이 구조적 한계 때문에 GPT 파티션 테이블이 등장했습니다.</p>
<hr>
<h2 id="parted-사용-예시" tabindex="-1" data-src-line="208">parted 사용 예시 <a class="header-anchor" href="#parted-사용-예시" aria-hidden="true">#</a></h2>
<p><code>parted</code>는 자동화 친화적이라서,<br>
실습에서도 “명령 한 줄로 구조를 만드는 느낌”을 보기 좋습니다.</p>
<p>아래 예시는 <code>/dev/sdc</code> 디스크를 GPT 방식으로 초기화하고,<br>
400M + 나머지 공간으로 파티션을 나누는 흐름입니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">parted</span> /dev/sdc
<span class="hljs-attribute">mklabel</span> gpt
<span class="hljs-attribute">mkpart</span> primary <span class="hljs-number">0</span>% <span class="hljs-number">400</span>M
<span class="hljs-attribute">mkpart</span> primary <span class="hljs-number">400</span>M <span class="hljs-number">100</span>%
<span class="hljs-attribute">print</span>
</code></pre></div></code></pre>
<h3 id="주의할-점" tabindex="-1" data-src-line="224">주의할 점 <a class="header-anchor" href="#주의할-점" aria-hidden="true">#</a></h3>
<p><code>parted</code>는 <code>fdisk</code>처럼 “마지막에 저장(w)”하는 느낌이 약합니다.<br>
명령이 곧바로 반영될 수 있어, 실수했을 때 되돌리기가 어렵습니다.</p>
<p>그래서 운영에서는 보통</p>
<ul>
<li>작업 전 <code>lsblk</code>로 대상 디스크 확인</li>
<li>작업 후 <code>print</code>로 결과 확인</li>
</ul>
<p>이 두 단계를 습관처럼 붙여서 진행합니다.</p>
<hr>
<h2 id="파티션-이후-선택지" tabindex="-1" data-src-line="238">파티션 이후 선택지 <a class="header-anchor" href="#파티션-이후-선택지" aria-hidden="true">#</a></h2>
<p>파티션을 만들었다면, 이 블록 디바이스는 세 가지 용도로 사용할 수 있습니다.</p>
<ol>
<li>파일시스템 생성 후 마운트</li>
<li>swap 영역으로 사용</li>
<li>raw 디바이스로 사용 (DB 등 특수 용도)</li>
</ol>
<p>일반적인 서버 환경에서는 1번과 2번이 대부분입니다.</p>
<hr>
<h2 id="파일시스템-생성" tabindex="-1" data-src-line="250">파일시스템 생성 <a class="header-anchor" href="#파일시스템-생성" aria-hidden="true">#</a></h2>
<p>파티션이 생성되면, 그 위에 파일시스템을 만들어야 실제로 사용할 수 있습니다.<br>
이번 실습에서는 <code>/dev/sdb1</code> 파티션을 <strong>XFS 파일시스템으로 포맷</strong>합니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>mkfs -t xfs <span class="hljs-regexp">/dev/</span>sdb1
lsblk -f
</code></pre></div></code></pre>
<h3 id="파일시스템은-포맷입니다" tabindex="-1" data-src-line="260">파일시스템은 ‘포맷’입니다 <a class="header-anchor" href="#파일시스템은-포맷입니다" aria-hidden="true">#</a></h3>
<p><code>mkfs</code>는 “파일을 만드는 명령”이 아니라,<br>
해당 블록 디바이스 위에 <strong>파일시스템 구조(메타데이터)를 새로 깔아버리는 작업</strong>입니다.</p>
<p>그래서 대상 디바이스를 잘못 지정하면 그대로 데이터가 날아갑니다.<br>
실습에서는 괜찮지만 운영에서는 항상 한 번 더 확인하는 습관이 필요합니다.</p>
<h3 id="왜-xfs를-많이-쓰는가" tabindex="-1" data-src-line="268">왜 XFS를 많이 쓰는가 <a class="header-anchor" href="#왜-xfs를-많이-쓰는가" aria-hidden="true">#</a></h3>
<p>요즘 RHEL 계열의 기본 파일시스템은 XFS입니다.</p>
<ul>
<li>ext 계열보다 대용량에 유리</li>
<li>온라인 확장 지원</li>
</ul>
<p>다만 모든 경우에 XFS가 정답인 것은 아닙니다.<br>
디스크 검사/복구 방식이 ext 계열과 다르므로, 운영 기준에 맞춰 선택하는 편이 안전합니다.</p>
<h3 id="uuid-확인" tabindex="-1" data-src-line="278">UUID 확인 <a class="header-anchor" href="#uuid-확인" aria-hidden="true">#</a></h3>
<p><code>lsblk -f</code>를 사용하면 파일시스템 타입과 UUID를 함께 확인할 수 있습니다.<br>
나중에 <code>/etc/fstab</code>에 등록할 때 UUID가 필요합니다.</p>
<hr>
<h2 id="마운트와-언마운트" tabindex="-1" data-src-line="285">마운트와 언마운트 <a class="header-anchor" href="#마운트와-언마운트" aria-hidden="true">#</a></h2>
<p>파일시스템을 만들었으면, 이제 경로에 붙여서 실제로 사용합니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-built_in">mkdir</span> /red
mount /dev/sdb1 /red
<span class="hljs-built_in">df</span> -h
</code></pre></div></code></pre>
<h3 id="mount는-연결입니다" tabindex="-1" data-src-line="295">mount는 ‘연결’입니다 <a class="header-anchor" href="#mount는-연결입니다" aria-hidden="true">#</a></h3>
<p>마운트는 디스크를 “복사”하는 게 아니라,<br>
특정 경로에 파일시스템을 <strong>연결</strong>하는 작업입니다.</p>
<p>그래서 마운트되기 전에는 <code>/red</code>가 빈 폴더였지만,<br>
마운트 이후에는 <code>/dev/sdb1</code>의 루트가 <code>/red</code>에 나타납니다.</p>
<h3 id="언마운트" tabindex="-1" data-src-line="303">언마운트 <a class="header-anchor" href="#언마운트" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>umount /red
</code></pre></div></code></pre>
<p><code>umount</code>는 장치를 떼어내는 작업입니다.<br>
파일을 열어둔 상태라면 실패할 수 있으니,<br>
필요하면 <code>lsof</code>나 <code>fuser</code>로 점유 프로세스를 확인하기도 합니다.</p>
<h3 id="재부팅하면-왜-사라지는가" tabindex="-1" data-src-line="313">재부팅하면 왜 사라지는가 <a class="header-anchor" href="#재부팅하면-왜-사라지는가" aria-hidden="true">#</a></h3>
<p><code>mount</code>는 커널 메모리 위에 “현재 연결 상태”를 올리는 작업입니다.<br>
재부팅하면 커널이 초기화되기 때문에, 마운트도 사라집니다.</p>
<p>그래서 영구적으로 사용하려면 <code>/etc/fstab</code>에 등록해야 합니다.</p>
<hr>
<h2 id="etcfstab-이해하기" tabindex="-1" data-src-line="322">/etc/fstab 이해하기 <a class="header-anchor" href="#etcfstab-이해하기" aria-hidden="true">#</a></h2>
<p><code>fstab</code>은 “부팅할 때 어떤 파일시스템을 어디에 붙일지”를 정의하는 파일입니다.<br>
운영에서는 장치 이름(<code>/dev/sdb1</code>) 대신 UUID를 쓰는 편이 안전합니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-built_in">cat</span> /etc/fstab
</code></pre></div></code></pre>
<h3 id="각-필드-의미" tabindex="-1" data-src-line="331">각 필드 의미 <a class="header-anchor" href="#각-필드-의미" aria-hidden="true">#</a></h3>
<ol>
<li>장치 이름 또는 UUID</li>
<li>마운트 지점</li>
<li>파일시스템 타입</li>
<li>마운트 옵션</li>
<li>dump 옵션 (현재는 거의 사용 안 함)</li>
<li>fsck 검사 순서</li>
</ol>
<p>XFS는 fsck를 사용하지 않기 때문에 보통 0으로 설정합니다.</p>
<h3 id="예시" tabindex="-1" data-src-line="342">예시 <a class="header-anchor" href="#예시" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">UUID</span><span class="hljs-operator">=</span>xxxx-xxxx  /red  xfs  defaults  <span class="hljs-number">0</span>  <span class="hljs-number">0</span>
</code></pre></div></code></pre>
<h3 id="작성-후-검증" tabindex="-1" data-src-line="348">작성 후 검증 <a class="header-anchor" href="#작성-후-검증" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>mount -<span class="hljs-selector-tag">a</span>
</code></pre></div></code></pre>
<p><code>mount -a</code>는 fstab에 적힌 항목을 실제로 마운트해보는 테스트입니다.<br>
오타가 있으면 여기서 바로 걸립니다.</p>
<hr>
<h2 id="swap-영역" tabindex="-1" data-src-line="359">Swap 영역 <a class="header-anchor" href="#swap-영역" aria-hidden="true">#</a></h2>
<p>Swap은 메모리가 부족할 때를 대비한 안전장치입니다.<br>
실습에서는 **파일시스템용 디스크(sdb)**와 분리해서,<br>
OS 디스크(<code>/dev/sda</code>) 안에 swap 파티션이 있다고 가정하고 설명합니다.</p>
<blockquote>
<p>실제 환경에서는 설치 과정에서 이미 swap이 잡혀 있는 경우가 많습니다.<br>
<code>lsblk -f</code>로 swap 타입이 있는지 먼저 확인하는 편이 안전합니다.</p>
</blockquote>
<h3 id="swap-장치-확인" tabindex="-1" data-src-line="368">swap 장치 확인 <a class="header-anchor" href="#swap-장치-확인" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">lsblk -f
swapon -s</span>
</code></pre></div></code></pre>
<p>이미 활성화된 swap이 있다면 <code>swapon -s</code>에 표시됩니다.</p>
<h3 id="swap-만들기활성화" tabindex="-1" data-src-line="377">swap 만들기/활성화 <a class="header-anchor" href="#swap-만들기활성화" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>mkswap <span class="hljs-regexp">/dev/</span>sda2
swapon <span class="hljs-regexp">/dev/</span>sda2
swapon -s
</code></pre></div></code></pre>
<ul>
<li>파일 스왑: 과거 방식, 권장하지 않음</li>
<li>디바이스 스왑: 현재 표준</li>
</ul>
<p>priority 값으로 사용 우선순위를 조절할 수 있습니다.</p>
<h3 id="fstab에-등록" tabindex="-1" data-src-line="390">fstab에 등록 <a class="header-anchor" href="#fstab에-등록" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">UUID</span>=yyyy-yyyy  none  swap  defaults,<span class="hljs-attribute">pri</span>=2  0  0
</code></pre></div></code></pre>
<hr>
<h2 id="lvm의-등장-이유" tabindex="-1" data-src-line="398">LVM의 등장 이유 <a class="header-anchor" href="#lvm의-등장-이유" aria-hidden="true">#</a></h2>
<p>디스크와 파티션만으로는 확장과 축소가 불편합니다.</p>
<p>예를 들어 <code>/dev/sdb1</code>에 파일시스템을 만들어 쓰다가 공간이 부족해졌다면,<br>
전통적인 방식에서는</p>
<ul>
<li>새 디스크를 붙이고</li>
<li>다시 파티션을 만들고</li>
<li>데이터를 옮기거나</li>
<li>서비스 중단을 고민해야 했습니다.</li>
</ul>
<p>LVM은 이 문제를 해결하기 위해 등장했습니다.</p>
<h3 id="lvm-계층-구조" tabindex="-1" data-src-line="412">LVM 계층 구조 <a class="header-anchor" href="#lvm-계층-구조" aria-hidden="true">#</a></h3>
<ul>
<li>PV(Physical Volume) → 물리 디스크/파티션을 LVM이 쓸 수 있게 만든 단위</li>
<li>VG(Volume Group) → 여러 PV를 묶어 만든 “저장소 풀”</li>
<li>LV(Logical Volume) → 실제로 사용하는 논리 볼륨(파일시스템을 올리는 대상)</li>
</ul>
<hr>
<h2 id="lvm-확장-흐름-실습" tabindex="-1" data-src-line="420">LVM 확장 흐름 실습 <a class="header-anchor" href="#lvm-확장-흐름-실습" aria-hidden="true">#</a></h2>
<p>앞선 실습에서 <code>/dev/sdc</code> 디스크는 아직 사용되지 않은 상태입니다.<br>
이 디스크를 <strong>LVM 확장용 디스크</strong>로 활용합니다.</p>
<h3 id="전체-흐름" tabindex="-1" data-src-line="425">전체 흐름 <a class="header-anchor" href="#전체-흐름" aria-hidden="true">#</a></h3>
<p>디스크 추가 → PV 생성 → VG 확장 → LV 확장 → 파일시스템 확장</p>
<p>이 순서를 반드시 지켜야 합니다.</p>
<h3 id="1-pv-생성" tabindex="-1" data-src-line="431">1) PV 생성 <a class="header-anchor" href="#1-pv-생성" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>pvcreate <span class="hljs-regexp">/dev/</span>sdc
pvs
</code></pre></div></code></pre>
<p><code>pvcreate</code>는 디스크를 LVM이 관리할 수 있는 형태로 초기화합니다.<br>
이 작업 이후부터 <code>/dev/sdc</code>는 “그냥 디스크”가 아니라 LVM의 PV로 취급됩니다.</p>
<h3 id="2-vg-확장" tabindex="-1" data-src-line="441">2) VG 확장 <a class="header-anchor" href="#2-vg-확장" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>vgextend vgcolor <span class="hljs-regexp">/dev/</span>sdc
vgs
</code></pre></div></code></pre>
<p>VG의 용량만 늘어난 상태입니다.<br>
아직 LV나 파일시스템의 크기는 변하지 않습니다.</p>
<h3 id="3-lv-확장" tabindex="-1" data-src-line="451">3) LV 확장 <a class="header-anchor" href="#3-lv-확장" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">lvextend</span> -L <span class="hljs-number">960</span>M /dev/vgcolor/lvred
<span class="hljs-attribute">lvextend</span> -l <span class="hljs-number">60</span> /dev/vgcolor/lvblue
<span class="hljs-attribute">lvs</span>
</code></pre></div></code></pre>
<p>여기까지는 블록 디바이스(LV) 크기만 늘어납니다.</p>
<h3 id="4-파일시스템-확장" tabindex="-1" data-src-line="461">4) 파일시스템 확장 <a class="header-anchor" href="#4-파일시스템-확장" aria-hidden="true">#</a></h3>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-built_in">df</span> -h
xfs_growfs /dev/vgcolor/lvred
resize2fs /dev/vgcolor/lvblue
<span class="hljs-built_in">df</span> -h
</code></pre></div></code></pre>
<ul>
<li>XFS는 <code>xfs_growfs</code></li>
<li>ext4는 <code>resize2fs</code></li>
</ul>
<p>여기까지 해야 실제로 <code>df -h</code>에서 용량이 늘어난 것이 보입니다.</p>
<h3 id="왜-두-번-늘려야-하는가" tabindex="-1" data-src-line="475">왜 두 번 늘려야 하는가 <a class="header-anchor" href="#왜-두-번-늘려야-하는가" aria-hidden="true">#</a></h3>
<p>LVM은 “디스크/볼륨” 크기를 다루고,<br>
파일시스템은 “그 위에 올라간 구조”를 다룹니다.</p>
<p>그래서 <code>lvextend</code>로 LV를 늘렸다고 해서<br>
파일시스템이 자동으로 커지지 않습니다.</p>
<hr>
<h2 id="lvm-축소-시-주의점" tabindex="-1" data-src-line="485">LVM 축소 시 주의점 <a class="header-anchor" href="#lvm-축소-시-주의점" aria-hidden="true">#</a></h2>
<p>축소는 확장보다 훨씬 조심해야 합니다.<br>
순서를 잘못 잡으면 데이터가 잘립니다.</p>
<h3 id="안전한-순서" tabindex="-1" data-src-line="490">안전한 순서 <a class="header-anchor" href="#안전한-순서" aria-hidden="true">#</a></h3>
<ol>
<li>파일시스템 축소</li>
<li>(필요 시 검사)</li>
<li>LV 축소</li>
</ol>
<p>ext 계열에서는 보통 아래 흐름으로 진행합니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>umount /blue

e2fsck -f /dev/vgcolor/lvblue
resize2fs /dev/vgcolor/lvblue 800M
lvreduce -L 800M /dev/vgcolor/lvblue
</code></pre></div></code></pre>
<p>XFS는 온라인/오프라인을 막론하고 <strong>축소를 지원하지 않기 때문에</strong>,<br>
XFS 파일시스템을 줄이는 실습은 일반적으로 “재구성(백업→재생성→복원)”으로 접근합니다.</p>
<p>그래서 운영에서는</p>
<ul>
<li>XFS는 확장 중심으로 설계</li>
<li>축소가 필요하면 ext 계열을 고려</li>
</ul>
<p>처럼 처음 설계 단계에서 선택이 갈리는 경우도 있습니다.</p>
<hr>
<h2 id="lvm-캐시와-태깅" tabindex="-1" data-src-line="518">LVM 캐시와 태깅 <a class="header-anchor" href="#lvm-캐시와-태깅" aria-hidden="true">#</a></h2>
<p>여기부터는 “필수 기능”이라기보다,<br>
디스크가 많아지고 운영 기간이 길어질수록 체감이 커지는 기능들입니다.</p>
<h3 id="lvm-캐시cache" tabindex="-1" data-src-line="523">LVM 캐시(Cache) <a class="header-anchor" href="#lvm-캐시cache" aria-hidden="true">#</a></h3>
<p>SSD를 캐시로 활용해 HDD 성능을 보완할 수 있습니다.</p>
<h4 id="write-through" tabindex="-1" data-src-line="527">write-through <a class="header-anchor" href="#write-through" aria-hidden="true">#</a></h4>
<p>데이터가 HDD와 캐시에 동시에 기록됩니다.<br>
안정성이 높지만 쓰기 성능 향상은 제한적입니다.</p>
<h4 id="write-back" tabindex="-1" data-src-line="532">write-back <a class="header-anchor" href="#write-back" aria-hidden="true">#</a></h4>
<p>데이터가 먼저 캐시에 기록되고, 이후 HDD에 반영됩니다.<br>
성능은 좋지만 장애 상황에서 데이터 유실 위험이 커집니다.</p>
<p>운영 환경에서 어떤 모드를 쓸지는 “성능”보다 “복구 전략”과 연결됩니다.</p>
<h3 id="lvm-태깅tagging" tabindex="-1" data-src-line="539">LVM 태깅(Tagging) <a class="header-anchor" href="#lvm-태깅tagging" aria-hidden="true">#</a></h3>
<p>태깅은 PV/VG/LV에 <strong>라벨처럼 메타 정보를 붙이는 기능</strong>입니다.</p>
<ul>
<li>용도별 분류(예: data, cache, backup)</li>
<li>운영/개발/테스트 구분</li>
<li>스크립트에서 특정 볼륨만 선택</li>
</ul>
<p>디스크가 많아지면 구조를 문서 없이 파악하기 어렵습니다.<br>
그럴 때 태깅이 관리 난이도를 낮춰줍니다.</p>
<hr>
<h2 id="정리" tabindex="-1" data-src-line="552">정리 <a class="header-anchor" href="#정리" aria-hidden="true">#</a></h2>

<li>항상 **계층 구조(PV → VG → LV → FS)**를 의식해야 합니다.</li>
<li>명령어보다 흐름을 이해하는 것이 중요합니다.</li>
</ul>
