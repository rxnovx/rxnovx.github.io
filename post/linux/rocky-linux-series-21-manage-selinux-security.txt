<p>SELinux는 이름만 들어도 부담을 느끼는 경우가 많습니다.<br>
실제로도 리눅스를 어느 정도 사용하다가 처음으로 &quot;SELinux 때문에 안 된다&quot;라는 상황을 겪으면, 가장 먼저 끄고 싶어지는 대상이기도 합니다.</p>
<p>하지만 SELinux는 단순한 옵션이 아니라, <strong>리눅스 보안 모델의 방향 자체를 바꾼 핵심 구성 요소</strong>입니다.<br>
이 글에서는 명령어 나열보다는,</p>
<ul>
<li>SELinux가 왜 만들어졌는지</li>
<li>어떤 보안 모델을 기반으로 동작하는지</li>
<li>실무에서 문제가 생겼을 때 어떤 순서로 접근해야 하는지</li>
</ul>
<p>이 흐름을 중심으로 정리해보려 합니다.</p>
<hr>
<h2 id="selinux-security-framework" tabindex="-1" data-src-line="18">SELinux Security Framework <a class="header-anchor" href="#selinux-security-framework" aria-hidden="true">#</a></h2>
<p>SELinux(Security-Enhanced Linux)는 <strong>NSA가 주도하여 설계한 강제 접근 제어(MAC) 기반 보안 프레임워크</strong>입니다.<br>
오픈소스 리눅스 환경에서 기존 권한 모델의 한계를 보완하기 위해 만들어졌습니다.</p>
<p>핵심은 하나입니다.</p>
<blockquote>
<p>“퍼미션이 맞아도, 정책이 허용하지 않으면 접근할 수 없다”</p>
</blockquote>
<p>이를 이해하려면 먼저 리눅스의 접근 제어 모델을 구분해서 볼 필요가 있습니다.</p>
<hr>
<h2 id="리눅스-접근-제어-모델-3가지" tabindex="-1" data-src-line="31">리눅스 접근 제어 모델 3가지 <a class="header-anchor" href="#리눅스-접근-제어-모델-3가지" aria-hidden="true">#</a></h2>
<h3 id="dac-discretionary-access-control" tabindex="-1" data-src-line="33">DAC (Discretionary Access Control) <a class="header-anchor" href="#dac-discretionary-access-control" aria-hidden="true">#</a></h3>
<p>임의 접근 제어 모델입니다.<br>
파일과 디렉터리의 <strong>소유자(owner)</strong> 가 접근 권한을 결정합니다.</p>
<ul>
<li>chmod</li>
<li>chown</li>
<li>rwx 퍼미션</li>
</ul>
<p>우리가 일반적으로 알고 있는 리눅스 권한 시스템은 모두 DAC 기반입니다.</p>
<p>문제는,<br>
소유자가 실수로 권한을 열어버리면 시스템 전체가 위험해질 수 있다는 점입니다.</p>
<hr>
<h3 id="mac-mandatory-access-control" tabindex="-1" data-src-line="49">MAC (Mandatory Access Control) <a class="header-anchor" href="#mac-mandatory-access-control" aria-hidden="true">#</a></h3>
<p>강제 접근 제어 모델입니다.<br>
<strong>사용자 의도와 상관없이 정책이 최우선</strong>으로 적용됩니다.</p>
<p>SELinux는 이 MAC 모델을 기반으로 설계되었습니다.</p>
<ul>
<li>정책(policy)에 의해 접근 허용 여부 결정</li>
<li>중앙 집중적 제어 가능</li>
<li>퍼미션보다 항상 우선</li>
</ul>
<p>SELinux가 &quot;까다롭다&quot;고 느껴지는 이유가 바로 여기에 있습니다.</p>
<hr>
<h3 id="rbac--rac-role-based-access-control" tabindex="-1" data-src-line="64">RBAC / RAC (Role-Based Access Control) <a class="header-anchor" href="#rbac--rac-role-based-access-control" aria-hidden="true">#</a></h3>
<p>역할 기반 접근 제어 모델입니다.</p>
<ul>
<li>사용자에게 역할(role)을 부여</li>
<li>역할에 따라 수행 가능한 작업 제한</li>
</ul>
<p>SELinux 내부에서도 role 개념이 존재하지만,<br>
실무에서는 type 중심으로 다루는 경우가 대부분입니다.</p>
<hr>
<h2 id="selinux의-작동-흐름" tabindex="-1" data-src-line="76">SELinux의 작동 흐름 <a class="header-anchor" href="#selinux의-작동-흐름" aria-hidden="true">#</a></h2>
<p>SELinux는 접근 요청이 발생하면 다음 순서로 판단합니다.</p>
<ol>
<li><strong>기본 퍼미션(DAC) 확인</strong></li>
<li><strong>Security Context 확인</strong></li>
<li>정책에 따라 허용 또는 차단</li>
</ol>
<p>여기서 핵심은 2번입니다.</p>
<hr>
<h2 id="security-context-구조" tabindex="-1" data-src-line="88">Security Context 구조 <a class="header-anchor" href="#security-context-구조" aria-hidden="true">#</a></h2>
<p>SELinux는 모든 프로세스와 파일에 <strong>보안 꼬리표(Security Context)</strong> 를 붙여 관리합니다.</p>
<p>형식은 다음과 같습니다.</p>
<pre><code><div class="code-block"><div class="code-header"><span class="code-title">unknown</span><button class="copy-button">Copy</button></div><pre class="language-plain"><code><span class="hljs-keyword">identity</span>:<span class="hljs-keyword">role</span>:<span class="hljs-keyword">type</span>:<span class="hljs-keyword">level</span>
</code></pre></div></code></pre>
<p>이 중 실무에서 가장 중요한 것은 <strong>type</strong> 입니다.</p>
<ul>
<li>프로세스 타입</li>
<li>파일 타입</li>
</ul>
<p>이 둘의 조합이 정책에 정의되어 있어야 접근이 허용됩니다.</p>
<hr>
<h2 id="security-context-확인-방법" tabindex="-1" data-src-line="107">Security Context 확인 방법 <a class="header-anchor" href="#security-context-확인-방법" aria-hidden="true">#</a></h2>
<p>아래 명령어들은 반드시 익숙해져야 합니다.</p>
<ul>
<li>현재 사용자 컨텍스트 확인</li>
</ul>
<pre><code><div class="code-block"><div class="code-header"><span class="code-title">unknown</span><button class="copy-button">Copy</button></div><pre class="language-plain"><code><span class="hljs-built_in">id</span>
</code></pre></div></code></pre>
<ul>
<li>파일 컨텍스트 확인</li>
</ul>
<pre><code><div class="code-block"><div class="code-header"><span class="code-title">unknown</span><button class="copy-button">Copy</button></div><pre class="language-plain"><code><span class="hljs-built_in">ls</span> -lZ
</code></pre></div></code></pre>
<ul>
<li>프로세스 컨텍스트 확인</li>
</ul>
<pre><code><div class="code-block"><div class="code-header"><span class="code-title">unknown</span><button class="copy-button">Copy</button></div><pre class="language-plain"><code><span class="hljs-attribute">ps -eZ</span>
</code></pre></div></code></pre>
<p>SELinux 트러블슈팅의 시작은 항상 <strong>타입 확인</strong>입니다.</p>
<hr>
<h2 id="relabeling-files-컨텍스트-복구" tabindex="-1" data-src-line="133">Relabeling Files (컨텍스트 복구) <a class="header-anchor" href="#relabeling-files-컨텍스트-복구" aria-hidden="true">#</a></h2>
<p>웹 디렉터리에 파일을 복사했는데 접근이 안 되는 경우는 매우 흔합니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>touch <span class="hljs-regexp">/var/</span>www<span class="hljs-regexp">/html/</span><span class="hljs-number">1</span>.html
touch <span class="hljs-regexp">/var/</span>www<span class="hljs-regexp">/html/</span><span class="hljs-number">2</span>.html
cp -a <span class="hljs-regexp">/etc/</span>passwd <span class="hljs-regexp">/var/</span>www<span class="hljs-regexp">/html/</span><span class="hljs-number">3</span>.html
</code></pre></div></code></pre>
<p>퍼미션만 보면 문제 없어 보이지만,<br>
<code>/etc/passwd</code>의 보안 컨텍스트는 웹 서비스와 전혀 맞지 않습니다.</p>
<hr>
<h3 id="chcon" tabindex="-1" data-src-line="148">chcon <a class="header-anchor" href="#chcon" aria-hidden="true">#</a></h3>
<ul>
<li>임시로 Security Context를 변경</li>
<li>타입을 정확히 알고 있을 때만 사용</li>
</ul>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>chcon -t httpd_sys_content_t <span class="hljs-regexp">/var/</span>www<span class="hljs-regexp">/html/</span><span class="hljs-number">3</span>.html
</code></pre></div></code></pre>
<p>재부팅이나 정책 재적용 시 원래대로 돌아갑니다.</p>
<hr>
<h3 id="restorecon" tabindex="-1" data-src-line="161">restorecon <a class="header-anchor" href="#restorecon" aria-hidden="true">#</a></h3>
<p>권장되는 방식입니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>restorecon -vFR /<span class="hljs-selector-tag">var</span>/www/<span class="hljs-selector-tag">html</span>
</code></pre></div></code></pre>
<ul>
<li>정책에 정의된 기본 컨텍스트로 복구</li>
<li>실무에서는 <strong>restorecon 우선</strong></li>
</ul>

<p>문제 해결 시 가장 먼저 확인해야 할 요소입니다.</p>

<h2 id="실습-ftp-업로드-차단-문제" tabindex="-1" data-src-line="257">실습: FTP 업로드 차단 문제 <a class="header-anchor" href="#실습-ftp-업로드-차단-문제" aria-hidden="true">#</a></h2>

</code></pre></div></code></pre>

<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code><span class="hljs-attribute">setsebool</span> -P ftpd_full_access <span class="hljs-literal">on</span>
</code></pre></div></code></pre>
<hr>
<h2 id="permissive-domains" tabindex="-1" data-src-line="275">Permissive Domains <a class="header-anchor" href="#permissive-domains" aria-hidden="true">#</a></h2>
<p>특정 서비스만 permissive로 설정할 수 있습니다.</p>
<pre><code class="language-bash"><div class="code-block"><div class="code-header"><span class="code-title">bash</span><button class="copy-button">Copy</button></div><pre class="language-bash"><code>semanage permissive -a <span class="hljs-type">httpd_t</span>
</code></pre></div></code></pre>
<p>전체 SELinux를 끄지 않고 문제 분석이 가능합니다.</p>
<hr>
<h2 id="selinux-트러블슈팅-접근-순서" tabindex="-1" data-src-line="287">SELinux 트러블슈팅 접근 순서 <a class="header-anchor" href="#selinux-트러블슈팅-접근-순서" aria-hidden="true">#</a></h2>
<ol>
<li>서비스 로그 확인</li>
<li><code>/var/log/messages</code> 또는 <code>journalctl</code></li>
<li><code>sealert -l</code> 실행</li>
<li>Boolean 여부 확인</li>
<li>port, type, context 점검</li>
</ol>
<p>SELinux 문제는 대부분 <strong>정책 위반 로그에 답이 이미 적혀 있습니다</strong>.</p>

<h2 id="마무리" tabindex="-1" data-src-line="299">마무리 <a class="header-anchor" href="#마무리" aria-hidden="true">#</a></h2>
<p>SELinux는 어렵기 때문이 아니라,<br>
<strong>제대로 된 흐름 없이 접근해서 어렵게 느껴지는 경우가 많습니다.</strong></p>
<ul>
<li>끄는 대신 이해하기</li>
<li>막연한 공포 대신 로그 읽기</li>
<li>퍼미션이 아니라 type부터 보기</li>
</ul>
<p>이 세 가지만 익숙해져도 SELinux는 더 이상 장애물이 아니라,<br>
시스템을 지켜주는 안전장치로 보이기 시작합니다.</p>
