<p>리눅스를 사용하다 보면 언젠가는 <strong>부팅이 정상적으로 되지 않는 상황</strong>을 마주하게 됩니다.<br>
서비스가 올라오지 않거나, 네트워크가 죽어 있거나, 심한 경우 로그인 자체가 불가능한 상태가 되기도 합니다.</p>
<p>이럴 때 필요한 것은 단순한 명령어 암기가 아니라,<br>
<strong>리눅스가 어떤 순서로 부팅되는지</strong>, 그리고 <strong>어디에서 문제가 발생했는지 추적할 수 있는 감각</strong>입니다.</p>
<p>이번 글에서는 Red Hat Enterprise Linux 계열(RHEL 7~10 기준)을 중심으로,</p>
<ul>
<li>리눅스 부팅 방식의 역사</li>
<li>systemd 기반 부팅 구조</li>
<li>Runlevel과 Target의 관계</li>
<li>싱글 유저 모드 진입과 암호 복구</li>
<li>서비스와 부팅의 관계</li>
<li>GRUB2와 커널 파라미터</li>
<li>initramfs의 역할</li>
</ul>
<p>을 <strong>실무에서 문제를 해결하는 관점</strong>으로 정리해봅니다.</p>
<hr>
<h2 id="리눅스-시스템-부팅-방식의-변화" tabindex="-1" data-src-line="24">리눅스 시스템 부팅 방식의 변화 <a class="header-anchor" href="#리눅스-시스템-부팅-방식의-변화" aria-hidden="true">#</a></h2>
<p>리눅스의 부팅 방식은 한 번에 systemd로 넘어온 것이 아닙니다.<br>
시대에 따라 점진적으로 발전해 왔습니다.</p>
<h3 id="runlevel-기반-system-v-init" tabindex="-1" data-src-line="29">Runlevel 기반 (System V init) <a class="header-anchor" href="#runlevel-기반-system-v-init" aria-hidden="true">#</a></h3>
<p>가장 오래된 방식입니다.<br>
부팅 시 특정 <strong>Runlevel</strong>에 따라 정해진 스크립트를 순서대로 실행합니다.</p>
<ul>
<li>각 Runlevel마다 시작/중지할 서비스 목록이 존재</li>
<li>순차 실행 방식</li>
<li>상용 UNIX 및 초기 리눅스 배포판에서 사용</li>
</ul>
<p>단순하지만 느리고, 의존성 관리가 어렵다는 단점이 있었습니다.</p>
<h3 id="event-기반-upstart" tabindex="-1" data-src-line="40">Event 기반 (Upstart) <a class="header-anchor" href="#event-기반-upstart" aria-hidden="true">#</a></h3>
<p>Ubuntu에서 시작된 방식으로,<br>
RHEL 6에서도 잠시 사용되었습니다.</p>
<ul>
<li>이벤트 발생 시 스크립트 실행</li>
<li>SysV init 구조를 기반으로 개선</li>
</ul>
<p>과도기적 성격이 강했고, 현재는 거의 사용되지 않습니다.</p>
<h3 id="dependency-기반-systemd" tabindex="-1" data-src-line="50">Dependency 기반 (systemd) <a class="header-anchor" href="#dependency-기반-systemd" aria-hidden="true">#</a></h3>
<p>현재 표준입니다.<br>
RHEL 7부터 본격적으로 도입되었습니다.</p>
<ul>
<li>서비스 간 <strong>의존성</strong>을 기반으로 병렬 실행</li>
<li>init 스크립트 대신 <strong>unit 파일</strong> 사용</li>
<li>시스템과 서비스 전체를 통합 관리</li>
</ul>
<p>부팅 속도와 관리 측면에서 가장 큰 개선이 이루어진 구조입니다.</p>
<hr>
<h2 id="init과-pid-1" tabindex="-1" data-src-line="63">init과 PID 1 <a class="header-anchor" href="#init과-pid-1" aria-hidden="true">#</a></h2>
<p>부팅 과정에서 커널이 가장 먼저 실행하는 사용자 공간 프로세스가 <strong>init</strong>입니다.</p>
<ul>
<li>PID 1</li>
<li>모든 프로세스의 부모</li>
<li>시스템 전체 수명 동안 유지</li>
</ul>
<p>과거에는 SysV init이 PID 1이었고,<br>
현재는 <strong>systemd가 PID 1</strong> 역할을 수행합니다.</p>
<p>이 차이를 이해하는 것이 매우 중요합니다.</p>
<hr>
<h2 id="systemd-핵심-개념-unit과-target" tabindex="-1" data-src-line="78">systemd 핵심 개념: Unit과 Target <a class="header-anchor" href="#systemd-핵심-개념-unit과-target" aria-hidden="true">#</a></h2>
<p>systemd를 이해하려면 두 가지 용어가 핵심입니다.</p>
<h3 id="unit" tabindex="-1" data-src-line="82">Unit <a class="header-anchor" href="#unit" aria-hidden="true">#</a></h3>
<p>systemd가 관리하는 모든 객체를 <strong>Unit</strong>이라고 부릅니다.</p>
<p>대표적인 유형은 다음과 같습니다.</p>
<ul>
<li>service : 서비스</li>
<li>target : 상태 묶음</li>
<li>mount : 마운트 포인트</li>
<li>socket : 소켓 기반 활성화</li>
<li>timer : 스케줄링</li>
</ul>
<h3 id="target" tabindex="-1" data-src-line="94">Target <a class="header-anchor" href="#target" aria-hidden="true">#</a></h3>
<p>Target은 <strong>여러 Unit의 묶음</strong>입니다.</p>
<p>과거 SysV init의 Runlevel에 해당하는 개념입니다.</p>
<hr>
<h2 id="runlevel과-target의-관계" tabindex="-1" data-src-line="102">Runlevel과 Target의 관계 <a class="header-anchor" href="#runlevel과-target의-관계" aria-hidden="true">#</a></h2>
<p>SysV init 시절의 Runlevel은 다음과 같았습니다.</p>
<ul>
<li>0 : 종료</li>
<li>1 : 싱글 유저 모드 (Rescue)</li>
<li>3 : 텍스트 모드 (멀티 유저)</li>
<li>5 : GUI 모드</li>
</ul>
<p>systemd에서는 이를 Target으로 대응시킵니다.</p>
<ul>
<li>runlevel 3 → multi-user.target</li>
<li>runlevel 5 → graphical.target</li>
</ul>
<p>내부적으로는 여전히 Runlevel 개념이 남아 있지만,<br>
<strong>운영 관점에서는 Target만 사용</strong>하는 것이 맞습니다.</p>
